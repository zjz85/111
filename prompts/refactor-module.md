## 1. Context（上下文定义）

### 项目背景

本项目是一个 PR 自动初评机器人。架构核心是三段式管道 + MCP Server 规范知识库 + 双模型复审：

```
orchestrator/        # 三段式主程序
  pipeline/
    stage1-fetch.ts  # Stage1: 读 PR + MCP 检查 + 高风险扫描
    stage2-review.ts # Stage2: 调 DeepSeek 评分（支持 chat/reasoner 切换）
    stage3-decide.ts # Stage3: 判定 pass/reject/escalate
  utils/
    diff-splitter.ts # diff 分片 + 有效行数
    mcp-client.ts    # MCP 客户端
    report-formatter.ts
mcp-server/          # MCP 规范知识库（Resource + Tool 注册模式）
skills/              # prompt 模板（review-prompt.md）
shared/              # 共享类型定义（types.ts）
data/                # JSON 数据（dual-model-records.json）

### 双区模型

- **探索区（exploration/）：** 原型实验，代码不受限制
- **生产区（production/）：** 正式代码，必须通过 4 条准入底线
- 从探索区迁移到生产区要走双区切换流程（填申请单→评审→迁移）

### 重构范围

- **项目区域：** □ 探索区（exploration/） □ 生产区（production/）
- **目标模块：** xxx 模块，文件路径 xxx
- **现状问题：** 当前模块存在 xxx 问题（如职责混杂、重复逻辑、可读性差、圈复杂度过高）
- **重构边界：** 仅调整模块内部实现，不改变对外功能与接口
- **定位：** 结构优化任务，不引入新功能，不修复非本次目标的业务 Bug

本任务以「结构收敛」为核心目标，严格控制变更范围，优先保障系统稳定性。生产区重构后还需要通过双区切换的 4 条准入标准。

## 2. Goal（目标声明）

在完全不改变外部行为与接口契约的前提下，完成目标模块的结构重构，具体目标：

- 拆分混杂职责，落实单一职责原则
- 收敛重复逻辑，统一规则的事实来源
- 降低模块认知复杂度，提升可读性与可测试性
- 保持所有现有行为与边界场景完全一致，无回归风险

---

## 3. Constraints（边界与约束）

### 契约刚性约束

- 对外暴露的所有接口签名、入参出参格式、异常语义、错误码完全保持兼容，调用方无需任何修改
- 对于 MCP Server 模块的 Resource/Tool：`registerResource`/`registerTool` 的 name、inputSchema 必须保持兼容
- 对于 orchestrator 模块的管道接口：Stage 间传递的数据结构（PreprocessedPR、ReviewResult、Verdict 等）不得破坏性变更
- 对于 `production/data/` 下的 JSON 文件（dual-model-records.json），数据结构必须保持向后兼容
- 核心业务逻辑、边界行为、异常处理逻辑与重构前完全一致，不引入功能变更
- 数据结构与持久化格式保持兼容，不破坏存量数据

### 复杂度约束

- 重构后模块的圈复杂度、认知复杂度不得高于原有版本
- 不新增不必要的第三方依赖，不扩大模块依赖范围
- 禁止为了「看起来优雅」引入过度抽象，优先保证可解释性

### 范围约束

- 重构严格限定在目标模块内，不扩散修改非相关文件
- 不夹带功能新增、Bug 修复等非重构目标的变更
- 所有变更必须可追溯、可回滚
- 探索区的重构不要求走双区切换流程，但迁移到生产区时必须补审

- **允许调整范围：** 模块内部的私有方法、内部类、实现细节、代码组织方式

## 5. Process（执行路径）

严格按以下顺序分步执行，禁止直接输出重构后全量代码，每一步确认后再推进。

1. **现状诊断：** 梳理目标模块当前的核心问题、职责边界、依赖关系与复杂度痛点。确认模块是否属于生产区核心模块，如是则重构后需通过双区切换评审
2. **方案设计：** 输出重构后的模块拆分设计、职责分配、调用关系，说明重构思路与预期收益
3. **代码实现：** 按方案输出重构后的内部代码实现，严格保留外部接口不变
4. **回归验证：** 列出所有需要回归验证的测试点与边界场景，确保行为一致性。用 exploration/sample-prs/ 下的数据验证不破坏现有评审流程
5. **影响说明：** 输出本次重构的变更范围、潜在风险、对上下游的影响评估

---

## 6. Review（验收与拒绝标准）

### 合格标准（全部满足方可通过）

- **兼容性：** 所有外部接口完全兼容，调用方无需任何修改
- **行为一致：** 核心业务逻辑、边界场景、异常处理与重构前完全一致
- **职责清晰：** 模块内职责拆分合理，单一职责原则落实，无职责堆叠
- **复杂度优化：** 重复逻辑被收敛，代码可读性提升，认知负担下降
- **可测试性：** 重构后代码更易编写单元测试，关键路径可独立验证
- **范围可控：** 变更严格限定在目标模块内，未扩大影响范围
- **生产区代码：** 还需满足 `docs/双区切换决策.md` 的 4 条准入标准

### 拒绝条件（命中任意一项直接打回重做）

- 改变了外部接口签名或行为语义
- 引入了功能变更或非预期的 Bug 修复
- 重构后复杂度反而升高
- 变更范围扩散到目标模块之外
- 无明确的回归验证方案
- 引入了未声明的新依赖或过度抽象
