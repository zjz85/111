## 1. Context（上下文定义）

### 项目背景

本项目是一个 PR 自动初评机器人。GitHub Actions 收到 PR 事件后启动 orchestrator 三段式管道：

```
Stage1 (Fetch & Split + MCP 规范检查) → Stage2 (调 DeepSeek API 做 4 维评分) → Stage3 (Decision Engine)
                                          ↕
                                     双模型复审（deepseek-reasoner）
```

规范知识库由 MCP Server 提供（15 条规则，5 个查询 Tool）。评分结果通过报告格式化 Skill 转成 Markdown 贴回 PR 评论区。

**双模型机制：** 当主审（deepseek-chat）结果处于边界（得分 3 分、标记 uncertain、或涉及敏感词）时，自动触发 deepseek-reasoner 复审。两轮结论不一致则强制转人工。双审记录写入 `production/data/dual-model-records.json`。

**CI 自动触发：** `.github/workflows/pr-review.yml` 在 PR 创建/更新/重开时自动跑全流程。

### 双区模型

- **探索区（exploration/）：** 原型实验、prompt 调试，代码不受限
- **生产区（production/）：** 正式代码，必须通过 4 条准入底线（可读、职责单一、无重复逻辑、服从架构）

### 技术栈

- MCP Server 用 `@modelcontextprotocol/sdk` + TypeScript
- 评审用 `openai` npm 包调 DeepSeek API（`deepseek-chat` 主审 / `deepseek-reasoner` 复审）
- 数据零散存储在 JSON 文件中（`production/data/`），不需要 ORM
- CI/CD 用 GitHub Actions（`.github/workflows/pr-review.yml`）

## 3. Constraints（边界与约束）

### 架构与职责约束

- 严格遵循项目分层：
  - MCP Server 层：用 `McpServer` 类 + `registerResource`/`registerTool`，不走 express/koa
  - orchestrator 层：三段式管道（stage1-fetch → stage2-review → stage3-decide），每段职责独立；utils/ 只放工具（diff-splitter、mcp-client、report-formatter）；pipeline/ 放核心业务逻辑
  - shared 层：只放类型定义和工具函数，不包含业务逻辑
- 单一职责原则：每个函数/类只承担一项核心职责，禁止出现上帝对象与职责堆叠
- 机制与策略分离：底层执行机制与业务策略规则解耦，策略可配置化，避免硬编码到实现中
- 探索区代码可放宽约束，生产区代码必须严格满足

### 依赖与兼容性约束

- 禁止引入未在需求中声明的第三方依赖；新增依赖必须说明必要性、替代方案与退出成本
- 保持接口向后兼容，不得破坏已有调用方的使用方式
- 所有接口定义参照 `docs/接口契约.md` 模板，包含入参、返回值、异常码
- 错误语义统一：异常处理遵循项目规范，所有失败路径均有明确可追踪的返回信息

### 复杂性预算约束

- 可读性优先：不追求炫技式精简写法，优先保证维护者可快速理解意图
- 无重复逻辑：同一业务规则不得在多处分散实现，优先复用现有公共逻辑
- 架构服从：新代码必须在既有架构中有明确位置，不得偏离系统主线
- 生产区代码必须参考 `docs/复杂性预算说明.md` 的 4 条准入底线和强制拒绝清单

严格按以下顺序分步执行，禁止一次性输出全部代码，每一步输出确认后再进入下一步。

## 6. Review（验收与拒绝标准）

### 合格标准（全部满足方可通过）

- **正确性：** 主路径逻辑正确，所有边界条件与失败场景均有处理，无未声明副作用
- **可读性：** 命名清晰表达意图，无魔法数字，控制流可见，维护者可快速理解代码逻辑
- **可维护性：** 无重复逻辑扩散，职责边界清晰，无跨层调用，技术债可控
- **可演进性：** 接口设计预留合理扩展空间，依赖轻量，机制与策略分离，未来调整成本可控
- **架构一致性：** 完全符合项目现有架构规范与代码风格，未偏离系统主线

### 拒绝条件（命中任意一项直接打回重做）

- 跨层级混写职责，破坏架构分层
- 引入未声明的第三方依赖
- 核心逻辑无对应单元测试覆盖
- 存在大量重复逻辑未收敛
- 错误语义不统一，失败路径不可追溯
- 命名与现有体系不一致，破坏概念完整性
